# A2v10 XAML Language Service — Architecture & Decisions

A Language Server for the `.vxaml` dialect (not `.xaml`, not `.axaml`) targeting Visual Studio 2026.
Goal: WPF-level IntelliSense — completion, diagnostics, hover, go-to-definition.

## Conventions

- **All code comments and log messages are in English.** No Russian. This applies to inline comments, XML doc comments, and string literals fed to `ExtensionLog` or any future logger. Identifiers stay in English regardless (default).

## Projects

| Project | Role |
|---|---|
| `XamlServiceExtension` | VSIX entry point. VS Extensibility SDK 17.14. Hosts the LSP server in-process. |
| `XamlLanguageServer` | LSP server library. OmniSharp. Handlers, resolvers, document store. |
| `XamlTolerantParser` | Lexer, parser, document model, xmlns extraction, `FindNodeAt`, `ContextAt`, `EditAt`. No VS / no LSP / no I/O dependencies. Pure CLR over source text. |
| `XamlTolerantParserTests` | xUnit tests for parser, xmlns extraction, find-node-at, position classification (`ContextAt`), on-type edits (`EditAt`). |

## Architecture — single in-process LSP server (proven end-to-end)

Everything — colouring, completion, on-type edits, diagnostics — is served by **one
in-process OmniSharp LSP server**. There is no second (TextMate) layer; the editor talks
LSP only.

### Hosting — LSP server (OmniSharp)
- Hosted **in-process** inside the extension. Transport: in-memory duplex channel (`Nerdbank.Streams.FullDuplexStream`).
- Framework: `OmniSharp.Extensions.LanguageServer`.
- Why in-process: in VS Extensibility (out-of-process model), `AppContext.BaseDirectory` points to the VS ServiceHub host — impossible to locate a sibling exe. In-process also enables F5 debugging of the server.
- `StartAsync` must be called **fire-and-forget** — `LanguageServer.From` waits for `initialize` from VS, which only arrives after the pipe is returned. Awaiting it causes a deadlock.
- **VS 2026 client capabilities are recorded** in a comment block above `XamlLangServer` (probed once by dumping `ClientCapabilities` at `initialize`). Facts that shape feature work: completion `SnippetSupport` / `CommitCharactersSupport` / `ContextSupport` / `InsertReplaceSupport` are all **false** (⇒ entry *selection* dispatches off `ContextAt`; plain single-range `TextEdit`s only). **But `ContextSupport=false` lies — VS sends `request.Context` anyway**: `TriggerCharacter` is populated, and on Backspace it is the *just-deleted text* (a `String`, possibly many chars). `CompletionHandler` drops the request when that text is non-empty and all-whitespace, killing the noise popup from deleting indentation/blank lines (removing `" "` from `AllCommitCharacters` does **not** help — the re-trigger isn't gated on commit chars). Hover is **plaintext-only**, push diagnostics are span+message only, and VS exposes the proprietary `_vs_onAutoInsert` and `LinkedEditingRange`. Re-probe if VS changes; see [memory: VS 2026 client capabilities](/.claude/memory/project_vs2026_client_capabilities.md).

### Syntax colouring — LSP semantic tokens (`SemanticTokensHandler`)
Colouring is **LSP semantic tokens**, not TextMate. (TextMate was tried first and
abandoned — see "Rejected approaches".) `SemanticTokensHandler : SemanticTokensHandlerBase`:
- **Static registration, not dynamic.** VS 2026 advertises `semanticTokens.dynamicRegistration = true` but does **not** honour a dynamic (`client/registerCapability`) registration of the semantic-tokens provider — so the handler is never invoked. `XamlLangServer.OnInitialize` clears the client's `SemanticTokens.DynamicRegistration` flag, forcing OmniSharp to declare `semanticTokensProvider` **statically** in the `initialize` response, which VS does honour. (Completion / onTypeFormatting are unaffected — VS honours *their* dynamic registration.) This was the one missing piece; without it colouring silently does nothing.
- **Full only** — `Full.Delta = false`, `Range = false`. vxaml files are small and the transport is the in-process duplex stream, so a full token list per change is cheap (and adds **no** extra parse — see below).
- **Legend echo.** The registration legend is the client's *own* advertised `TokenTypes` / `TokenModifiers` (guard the null — OmniSharp also calls `CreateRegistrationOptions` with no capability when folding into static server capabilities). Echoing means we can only ever name a type the client understands.
- **Source is the cached `XamlDocument` tree** (`DocumentStore`), walked by `XamlDocument.Visit(Action<XamlNode>)` — so a semantic-tokens request is a pure tree walk, no reparse. `Visit` descends into **all** structural branches, not just `Children` (attributes, values, extensions, args each live on their owning node).
- **Pure mapping + collect-then-sort.** `SemanticTokensHandler.Tokens(doc)` (unit-testable, no LSP builder) maps each colourable span to a `SemanticTokenType`, then **sorts by start position** before pushing — the builder delta-encodes and requires ascending order, but document order does not give it (an element's `CloseNameSpan` sits after its children yet `Visit` emits it in the element's pre-children visit). Multi-line spans (comment, CDATA, wrapped value) are split one-token-per-line (`PushSpan`) because the protocol cannot encode a token crossing a line.
- **Palette: three colours**, chosen to echo standard XML (eyeballed live; VS themes collapse the ~23 standard token types into a handful of distinct colours, and the type→colour mapping is the *theme's* job — a user remaps in Tools → Options → Fonts and Colors):
  - `String` — element tag names and markup-extension type names
  - `Type` — attribute names, extension argument names, positional arguments
  - `Keyword` — attribute values, extension argument values
  - `Comment` — comments **and CDATA** (both read as inert text)
  A positional argument's bare value and a named argument's value are both `XamlExtensionStringValue` but coloured differently, so they are coloured **via their parent argument node**, not in a standalone case. A nested extension is coloured by its own `XamlExtension` case on descent, never flattened into one value token.
- **Tests assert STRUCTURE, not the literal type** (`SemanticTokensTests`): the three role colours are *discovered* from minimal samples, then everything is compared against them (which entities share a colour, positional-vs-named distinction, nested-not-flattened, three roles distinct). So the palette can be retuned with **zero** test edits as long as the structure holds. (Lesson: the first cut hardcoded `String`/`Type`/`Keyword` and churned on every colour tweak — pin the invariant, not the cosmetic choice.)
- **Scope (decided):** colour only spans the parse tree exposes directly — names, values, comments, CDATA. Punctuation (`< > / = " { } ,`) and the xmlns prefix of a qualified name (`my:Button`) are **not** separately coloured (no dedicated span; a qualified name is coloured whole, prefix included).

## Rejected approaches (do not revisit without strong reason)

- **TextMate grammar for syntax colouring** — was the original Layer 1 (a `.plist` grammar copied from VS's built-in XAML, `scopeName` → `text.vxaml`, reusing the XML grammar + XAML theme). It *worked* when the grammar was dropped into the VS install folder by hand, but the new VS Extensibility (out-of-process) VSIX **cannot deliver a TextMate grammar** — there is no asset mechanism, and a hand-placed grammar is overwritten on every VS update. After a long fight with delivery, **abandoned in favour of LSP semantic tokens** (see Architecture). The earlier worry that "semantic tokens break colouring on malformed input (every keystroke)" did **not** materialise: the tolerant parser always yields a tree, so `Tokens` always returns a sensible set. The grammar project, `.plist`, pkgdef registration and the leftover `language-configuration.json` have all been removed.
- **`ITextViewTaggerProvider` / `ClassificationTag`** — classic MEF API, unavailable in the new VS Extensibility model without a hybrid VSIX.
- **Inheriting `.vxaml` from XML document type** — `DocumentTypeConfiguration.BaseDocumentType` is singular; setting it to XML breaks LSP.

**Root cause of the last two:** the new VS Extensibility model is isolated from the classic in-process editor infrastructure. The LSP server (semantic tokens, completion, diagnostics, on-type edits) is the bypass — everything goes through LSP.

- **Incremental parsing / `TextDocumentSyncKind.Incremental`** — vxaml documents are 100-200 lines typically, 1000 lines exceptional. A full reparse of a 50 KB file by the hand-written lexer (zero allocations, all spans are structs over the same source) takes ~100 µs–1 ms. Per-keystroke that is ≤10 ms/sec of CPU on the worst file we'll ever see — well below the noise floor on a budget dominated by assembly reflection, JSON, and VS rendering. Going incremental costs Roslyn-tier infrastructure (red-green tree or equivalent) to make position-offset updates after a splice cheap; the implementation is ~2000 lines of subtle code for a win that won't be measurable. `TextDocumentSyncKind.Incremental` separately would save nothing: the transport is the in-process `Nerdbank.Streams.FullDuplexStream` (memory copy, no network), and applying the delta still allocates a fresh full-length string. The two are independent — and neither is justified at our sizes.

## Assembly discovery — `@assemblies` convention

User puts the DLLs that the vxaml dialect references (`A2v10.Xaml.dll` etc.) into a folder literally named **`@assemblies`** somewhere above their `.vxaml` files. The server walks up the directory tree from a vxaml path until it finds one. That folder is the type universe for those files. No `project.assets.json`, no `PackageReference`, no `csproj` lookup, no VS Extensibility workspace queries — **pure file-system convention**.

**Discovery flow** in `AssemblyResolver`:
1. On `didOpen`/`didChange`, `TextDocumentSyncHandler` calls `_resolver.EnsureFolderFor(uri.GetFileSystemPath())`.
2. Resolver checks its `_anchors` list — if the new path starts with any known anchor (the *directory containing* `@assemblies`), nothing to do.
3. Otherwise walks `Path.GetDirectoryName` up until a directory with an `@assemblies` subfolder is found. Anchor + folder remembered.
4. If no `@assemblies` exists in the tree, nothing is registered. Lookups will return null silently.

A typical session sees 1-3 walk-ups total. Anchors live for the server lifetime; the per-tree-of-files cost is one `Directory.Exists` per ancestor.

**Loading & lookup** uses `System.Reflection.Metadata` — a `MetadataReader` over a `PEReader` — with **no `MetadataLoadContext`, no reflection, and no `System.Type` ever materialised.** `AssemblyResolver.GetAssembly(name)` finds `{name}.dll` in a registered `@assemblies` folder, reads its **bytes** once (`File.ReadAllBytes`), and hands them to `new PEReader(ImmutableArray<byte>)`. Reading bytes (rather than memory-mapping the file) means the DLL is **never locked** — the user can rebuild `A2v10.Xaml.dll` without killing VS. `XamlAssembly` consumes the `MetadataReader` and extracts everything it needs into plain strings during construction, so the `PEReader` can be disposed the moment the constructor returns (eager, like the old index).

**Why metadata, not MLC:** a language service that compares everything **by simple name** never needs a live `Type` or type identity. And a name lives physically in *this* file's tables: a `TypeRef` row stores the referenced type's name + namespace + `AssemblyRef` *as strings*, readable without loading the assembly that defines the type. MLC's whole job — resolving those refs into materialised `Type`s — is the wrong tool when you only want the strings (and it always resolves, dragging in `mscorlib`/BCL and throwing on any absent dependency). `MetadataReader` reads `TypeDef`/`TypeRef`/`TypeSpec` and signature blobs directly. Consequences:
- **No runtime-directory fallback, no `mscorlib` probe** — the entire MLC bootstrap is gone, and `@assemblies` does **not** need the BCL or sibling base assemblies present.
- **No transitive base-class closure requirement.** The base-class walk follows `TypeDefinition.BaseType` while it stays inside this file; a base that is a `TypeReference` (sibling assembly) or generic `TypeSpecification` is read **by name** and ends the walk — enough to match a dialect role marker (`RootContainer`, `UIElement`, `Dictionary\`2`, …). A missing sibling **never throws** — the reader stops at the name it already has. (The old MLC index threw on the first unresolvable ancestor; that "completeness is a hard requirement" gap is closed.)
- **Interfaces** are read from each type's `InterfaceImplementation` rows (directly-declared, no transitive resolution). The transitive closure *across the base-class chain* is reconstructed cheaply by also reading the interfaces of each same-file base class — so a type that inherits a dialect interface through a base (`SheetGroupCell : SheetCellGroup : ISheetCell`) is still recognised. Filtered to dialect (`A2v10.*`) namespaces.
- **Content-property element type** is decoded from signature blobs via `SignatureDecoder` (`MetaSignature`): `Rows : TableRowCollection : List<TableRow>` yields `TableRow`, all from this file — no `List<T>` resolution.
- **Enum values** come from the enum's literal static `Field` rows — but only when the enum is defined in the *same* file (its base is a readable `System.Enum` ref). A cross-file enum's values stay `null` (we don't open the other file).

**Stale cache:** a built `XamlAssembly` is cached by name for the server lifetime and not rebuilt when the DLL changes. Acceptable: vxaml types come from a stable controlled package; restart VS to pick up a new DLL version. No `FileSystemWatcher` needed.

## Parser & document model

**Syntax layer (done).** `XamlTolerantParser`:
- Tolerant, full reparse on every change (non-incremental). `XamlParser.Parse(string) → XamlDocument`.
- Lexer is hand-written (`XamlLexer`) with one-token pushback (`Back()`).
- Node hierarchy: `XamlNode` → `XamlElement`, `XamlText`, `XamlComment`, `XamlCData`, `XamlAttribute`, `XamlValue`, plus the markup-extension subtree (see below).
  - `XamlElement.OpenTagSpan` (`TextSpan?`) — the full `<name …>` / `<name …/>` extent, recorded when the open tag reaches its `>`/`/>`; **null** when it never does (EOF / recovery). Null is a third state with its own meaning ("the whole element is still the open tag"), consumed by `ClassifyInElement` and the `/` self-close guard.
  - `XamlAttribute` is **not** in `element.Children` — it lives in `element.Attributes`. Children are content nodes only.
  - `XamlValue` is owned by `XamlAttribute.Value`. Carries `Span` (whole value with quotes), `ContentSpan` (inside quotes), `Quote`, `IsUnterminated`, `Extension?`.
  - No `XamlMalformedNode` — malformed input is represented by diagnostics plus best-effort recovery into normal nodes, not by a distinct node type.
- **Markup extensions are parsed.** `XamlValue.Extension` is populated when the content of a quoted attribute value starts with `{` and isn't the `{}` literal-string escape (XAML spec).
  - Subtree: `XamlExtension` (carries `OpenBraceSpan`, `TypeNameSpan`, `CloseBraceSpan?`, `Arguments`, `IsClosed`) → `XamlExtensionArgument` (abstract) → `XamlPositionalArgument` | `XamlNamedArgument` (carries `NameSpan`, `EqualsSpan?`). The argument's `Value` is a `XamlExtensionValue` (abstract) → `XamlExtensionStringValue` (bare-text span) | `XamlExtension` (nested — extension is its own value type, no wrapper needed).
  - Driven by `MarkupExtensionParser` — a standalone mini-parser invoked from `XamlParser.MakeValue`. Operates strictly inside `ContentSpan`, appends diagnostics to the shared list. Keeping it separate from the main lexer/parser keeps the XML grammar uncontaminated by ME grammar and lets the mini-parser carry its own cursor state (line/col tracked the same way as the lexer).
  - Tolerance: unterminated `}` (`IsClosed=false` + diagnostic), empty type name (`{|`), trailing `=`/`,`, double `,`, nested extensions, escape `{}`. `<` and `>` are **barrier characters** in the mini-parser — when the outer attribute value is itself unterminated and `ContentSpan` runs to EOF, the extension span stops at the next `<` / `>` instead of swallowing the rest of the document.
  - The `\}` / `\\` escapes that the XAML markup-extension grammar formally supports are **not** implemented. They are vanishingly rare in vxaml; `\` inside a string value parses as a literal character. Add a `\`-escape branch in `MarkupExtensionParser.ParseValue` if a real use case appears.
- Every node has `Parent` set (root nodes have `Parent == null`). `XamlValue.Parent` is its `XamlAttribute`; an extension's parent chain walks back through any number of nested-extension layers to the `XamlAttribute` (see `XamlPositionClassifier.FindOwningAttribute`).
- Span invariant: a parent's `Span` always contains the spans of its attributes, values, children, and (when present) extension subtree (asserted by `Span_of_every_node_contains_spans_of_its_children`).
- Recovery covered: unclosed tags at EOF, mismatched close tags, inner unclosed tags closed by outer, stray `<` mid-tag, unterminated attribute values, unterminated comments/CDATA, broken sibling not poisoning later good siblings, plus all the markup-extension tolerance cases above. 238 tests in `XamlTolerantParserTests` (parser recovery + `ContextAt` + `EditAt` + `IdentifierSpanAt`).

- `XamlDocument` carries `Source` (the original string) and offers `TextOf(TextSpan)` — consumers substring by span without threading the source through every call.
- **`XamlDocument` also carries xmlns view of the document**, computed inline by `XmlnsExtraction` during `XamlParser.Parse`:
  - `ClrPrefixes: IReadOnlyDictionary<string, (string asm, string ns)>` — prefix (`""` for default) → CLR coordinates from `clr-namespace:Foo;assembly=Bar`.
  - `LanguagePrefixes: IReadOnlySet<string>` — prefixes bound to a `http(s)://` URL, marking them as the XAML language namespace (enables `{prefix}:Name`, `{prefix}:Key`, etc).
  - `AssemblyNames: string[]` — unique assemblies referenced by `ClrPrefixes`. Convenience projection.
  - No `XmlnsScope` / `XmlnsBinding` hierarchy / `XmlnsResolver` separate class — that was over-engineered. The data is just three flat fields on the document.

- **`FindNodeAt(int offset)`** — done. `XamlDocument.FindNodeAt(offset) → XamlNode?` returns the most specific node whose span contains the offset, or `null` if outside every root. Recursive descent with `SpanSearch.FindContaining` (binary search, O(log n) per level). Sibling spans are assumed non-overlapping and sorted by Start — guaranteed by the parser.
- **Whitespace-only character data is dropped by the parser** — no `XamlText` is emitted for `Content` tokens whose source is only ` `, `\t`, `\r`, `\n`. Significant text (including text that happens to have surrounding whitespace, like `"  hello  "`) is preserved verbatim. Reason: a language service has no use for whitespace nodes (no completion / hover / diagnostic uses them), and prettified files would otherwise triple the tree size with empty leaves. Consequence: in `FindNodeAt`, an offset inside whitespace between tags returns the parent element (or `null` if between roots), giving handlers immediate context instead of a useless empty leaf.

**Not yet implemented (planned):**
- **More `XamlContextProvider` consumers** — `HoverService`, type-aware diagnostics. `CompletionHandler` already reads from `XamlContextProvider.Complete` (tags / attribute names / values), which is fully on `ContextAt`; see "Type / context provision" for its current shape.

## Position representation — both offset and line/column

**`TextSpan` carries six fields**: `Start`, `Length` (offset arithmetic, for cheap `Source.Substring`) and `StartLine`, `StartColumn`, `EndLine`, `EndColumn` (LSP-shaped, 0-based, UTF-16 code units per column). The lexer walks the source character by character and tracks both in one pass.

Why both:
- LSP delivers `Position` as `(line, character)`. Storing only offsets forces every request to convert both ways.
- But some semantic logic (forward / backward source scans, substring extraction) inherently wants offsets. Carrying both means each consumer picks the cheaper axis with no `LineMap` round-trip.
- `LineMap` is deleted. The few places that still need an offset from an LSP position call `XamlDocument.OffsetAt(line, column)` (a one-shot linear scan over `Source`).

What the lexer does:
- Carries `int _line, _column`; snapshots them at every token start.
- On `\n`: `_line++`, `_column = 0`. `\r` is swallowed (no column change, no line change) — so CRLF behaves as a single break via `\n`, and lone `\r` is treated as a no-op. Files come from VS editors, where lone `\r` does not occur in practice.
- `Eof()` emits a zero-length span at the current `(_pos, _line, _column)` — the parser uses this to size unclosed elements out to EOF without consulting `_source.Length` separately.

What `XamlDocument` exposes:
- `FindNodeAt(int line, int column)` — line/column only. No offset overload; add one back when a consumer actually needs it.
- `OffsetAt(int line, int column)` — linear scan, used by source-scanning code (e.g. `IdentifierSpanAt`).
- `TextOf(TextSpan)` — substring via offsets.
- `IdentifierSpanAt(int line, int column)` — the run of name chars around the caret (back- + forward-walk over the source), the token a completion replaces. A pure text fact, independent of the parse tree, so it is immune to the half-open-span exclusive-end quirk. See "Type / context provision" → completion edit range.
- `Visit(Action<XamlNode>)` — pre-order walk of the whole tree in document order. Descends into **all** structural branches, not just `Children` — attributes (`element.Attributes`), values (`attribute.Value`), markup extensions (`value.Extension`), arguments (`extension.Arguments`) and argument values each live on their owning node. A `Children`-only walk would miss every attribute, value and extension. Drives semantic-tokens colouring (`SemanticTokensHandler.Tokens`); independently tested in `VisitTests`.

Span composition helpers on `TextSpan`:
- `FromTo(from, to)` — merge from `from.Start*` to `to.End*`.
- `FromToStart(from, to)` — extend `from` up to (not including) `to.Start*`. Used in recovery (close an unclosed tag at the start of the next sibling).

## Position classification

`XamlDocument.ContextAt(line, column) → XamlPositionContext` classifies a cursor position into a structural variant that completion / hover / diagnostics dispatch on. Implemented by `XamlPositionClassifier`. The contexts are a discriminated union of records (`OutsideContext`, `TagNameContext`, `ChildTagNameContext`, `EndTagNameContext`, `TagInteriorContext`, `AttributeNameContext`, `AttributeValueContext`, `ElementContentContext`, `TextContext`, `CommentContext`, `CDataContext`, plus the markup-extension family `ExtensionTypeNameContext`, `ExtensionInteriorContext`, `ExtensionArgNameContext`, `ExtensionArgValueContext`, `ExtensionPositionalArgContext`). Every variant carries the filtered list of diagnostics whose spans contain the cursor — handlers don't refilter.

`ExtensionArgValueContext` is the value slot of a **named** argument only (`Argument` is `XamlNamedArgument`); a positional/bare token has its own `ExtensionPositionalArgContext` (`Argument` is `XamlPositionalArgument`). The split is deliberate: the classifier owns the positional-vs-named discrimination so consumers dispatch on the variant alone — never a pattern-match on `Argument`. (vxaml has no real positional values; a bare token is just a name being typed, so completion treats it like an argument-name slot — see "Type / context provision".)

**Tag-name scope is split into two variants, never one with a nullable container.** Element-name completion lives in a clean 2×2 (scope × whether `<` was typed):

| | content (no `<` yet) | tag name (`<` typed) |
|---|---|---|
| **root scope** | `OutsideContext` | `TagNameContext` (Element?) |
| **child scope** | `ElementContentContext` (Element) | `ChildTagNameContext` (Element?, **Container**) |

`TagNameContext` is root-only and carries **no** container. `ChildTagNameContext.Container` is **non-nullable** — a child always has one. The root-vs-child decision is baked into the type by the classifier, so consumers (`XamlContextProvider.Complete`) dispatch with no guard clauses. The container is derived from the element the `<` sits inside (the partial tag's `OwnerElement`, or the enclosing element when no partial node exists yet, e.g. `<a><|`), **not** from `elem?.OwnerElement` alone — the latter is null in the empty-name case and would misroute a child position to root scope.

Algorithm in three steps:
1. `FindNodeAt(line, column)` once, reused everywhere. On a miss, one **trailing-edge retry**: an element whose close tag is missing *owns its trailing edge* — its half-open span ends at EOF and there is no next construct for the boundary position to belong to (the same rule `XamlValue.FindNodeAt` applies to an unclosed extension). `FindNodeAt(column-1)` is accepted iff it yields an element that is not self-closing, has no close tag **and has a complete open tag** (`OpenTagSpan != null`) — the last guard keeps `<Button |` at EOF (open tag never reached `>`) on the quiet `Outside` path instead of misrouting its edge to content.
2. If the node is a content / extension node (value, comment, cdata, extension, arg, string-value), classify by its runtime type. Three source-text probes precede the node switch:
   - `=` probe at the attribute level — cursor right after an attribute's `=` with no value yet (`<a b=|`) returns `AttributeValueContext(Value=null)`.
   - Tag-name probe — walk back over name chars; preceded by `<` ⇒ `TagNameContext` (root) or `ChildTagNameContext` (when a container is found), by `</` ⇒ `EndTagNameContext`. Handles the `<Butt|` / `</Butt|` cases where the cursor sits past every span's exclusive End.
   - Attribute-name probe — a value-less attribute's span ends at its name, so a cursor at the name's exclusive End (`<Button Wi|`) — or past every span at EOF — misses the attribute node (FindNodeAt returns the owning element or null, which would misroute to `TagInterior` / `Outside`). When name-chars sit to the left (and it is not a tag name), retry `FindNodeAt(column-1)`; if that is a `XamlAttribute`, return `AttributeNameContext`. This is what makes attribute-name completion fire *while typing* while leaving the empty interior slot (`<Button  |/>`, whitespace to the left) as `TagInterior`.
3. Otherwise switch on the node type (element / attribute / text / etc.). The element case (`ClassifyInElement`) is a pure span fact: inside `XamlElement.OpenTagSpan` (the full `<name …>` extent, recorded by the parser at `TagClose`/`SelfTagClose`) ⇒ `TagInterior`, past it ⇒ `ElementContent`; a **null** `OpenTagSpan` means the open tag never reached its `>` (EOF/recovery input), the whole element is still the open tag ⇒ `TagInterior`. (Replaced the old forward text scan `IsInsideOpenTag`, which false-positived on EOF after a *closed* open tag — `<Grid>\n  |` offered nothing.) The argument-node cases (cursor *inside* an arg span) emit `ExtensionPositionalArgContext` for a positional argument (and its string value) and `ExtensionArgValueContext` only for a named argument's value. The `XamlExtension` case (`ClassifyInExtension`) is for a cursor that landed on the extension itself — its type name, or a **gap** in the argument area (whitespace, or just past a half-open arg span). It is **structural and total** (see [memory: rules must be total](/.claude/memory/feedback_typical_over_exhaustive.md)): (i) inside/at-the-end-of the type name (`offset ∈ (OpenBraceSpan.Start, TypeNameSpan.End]`) → `ExtensionTypeNameContext`; (ii) otherwise a single backward scan — skip the token under the caret and the whitespace around it, then read the governing separator — yields **exactly two described outcomes**: a `=` owned by a parsed named arg → `ExtensionArgValueContext` (its value slot); the explicit catch-all → `ExtensionInteriorContext` (covers no-`=`, a `,` starting a new arg, the type-name/`{` boundary, and a malformed unowned `=`). Whitespace-insensitive **by construction** — never a `Source[offset-1]=='='` / `arg.Span.End==offset` adjacency coincidence (`{Bind Type=D |}`, `{Bind Type= |}` classify the same as the tight forms).

Boundary convention — "what's to the LEFT of the cursor":
- Cursor at the exclusive end of a name span (tag name, attribute name, extension type name) is still inside that name span. Pinned by `Right_after_tag_name_with_no_whitespace_is_still_TagName` (tags) and `Inside_extension_type_name_is_TypeName` (extensions). The user just finished typing — completion should still see the partial name.
- Cursor on whitespace immediately after a name is the *next* context (Interior / Arg slot). The tag/attribute probes walk back over name chars, so this falls out automatically; inside an extension the structural backward scan in `ClassifyInExtension` (step 3 above) does the same job, whitespace-insensitively, for the argument slots.

For unclosed extensions specifically, `XamlValue.FindNodeAt` descends into the extension even at its exclusive-end column — without that, `"{|"` (cursor right after `{`) would land on the surrounding `XamlValue` instead of the empty-type-name extension.

## On-type formatting (auto-edits)

`XamlDocument.EditAt(line, column, char ch) → XamlTypingEdit?` is the formatting sibling of `ContextAt`: given a freshly typed trigger character (already in `Source`, caret right after it) it returns the auto-edit to apply, or `null`. Implemented by `XamlTypingEditor`; driven by the LSP `textDocument/onTypeFormatting` handler (`OnTypeFormattingHandler`, trigger chars `>` `/` `"` `'` `` ` `` `{` `\n`). Proven end-to-end in VS 2026.

**`XamlTypingEdit(TextSpan Replace, string NewText)`** — a neutral, LSP-free edit; the server maps it 1:1 to a `TextEdit` (`Replace → Range`, `NewText`). **No explicit caret field:** VS 2026 derives the caret from the edit *shape* (verified live, see [memory: onTypeFormatting caret](/.claude/memory/project_ontypeformatting_caret.md)):
- an **empty `Replace` at the caret** leaves the caret to the **left** of `NewText`;
- a **`Replace` whose range END is the caret** moves the caret to the **end** of `NewText`;
- a `Replace` entirely to the **right** of the caret leaves the caret put.

The shape *is* the caret instruction, so a `(span, text)` pair suffices — no desired-caret field was needed.

**Behaviours** (`switch (ch)` in `XamlTypingEditor.Edit`):
- **`>` → insert matching close tag.** `<Button>|` ⇒ `<Button>|</Button>`. Empty `Replace` at the caret, `NewText = "</name>"`. Guarded: the element (from `FindNodeAt`) must be neither self-closing nor already closed; name from `OpenNameSpan`.
- **`/` → complete self-close.** `<Button/|` ⇒ `<Button/>|`. `Replace` of the just-typed `/`, `NewText = "/>"` (range ends at the caret ⇒ caret after `>`). Guarded by **`OpenTagSpan` containment**: the typed `/` must sit inside the element's open tag (null `OpenTagSpan` ⇒ open tag unclosed at EOF ⇒ the `/` is part of it ⇒ allowed). Without this, the `/` of a hand-typed close tag (`<Grid></|`) resolved to the element via `FindNodeAt` and got mangled into `<Grid></>`.
- **`/` → collapse a redundant close tag.** `<Grid|></Grid>` + `/` ⇒ `<Grid/|>` (the `</Grid>` is deleted). Fires only when, right after the existing `>`, the **literal** text `</name>` stands **immediately** there with a **matching name** — `Replace` = its span, `NewText = ""` (deletion is to the right of the caret, so the caret stays). **Deliberately strict** (see [memory: rules must be total](/.claude/memory/feedback_typical_over_exhaustive.md)) — but the not-firing is the *described* branch (not literally adjacent ⇒ deliberately do nothing, to avoid a wrong edit), not luck: no whitespace skipping, no content analysis — adjacency already implies the element is empty. The **name match is mandatory** — a partial child before a parent's close tag (`<StackPanel><Grid/></StackPanel>`) must not eat `</StackPanel>`.
- **Auto-closing pairs `"` `'` `` ` `` `{` → insert the closing counterpart.** `"|` ⇒ `"|"`, `{|` ⇒ `{|}`. `ClosePair` returns an empty `Replace` at the caret with `NewText` = the closing char — caret stays to the **left**, i.e. between the pair. **Dumb pairing, fires anywhere, no context analysis at all** (the user insisted — it is autocomplete, not a strict editor): no `FindNodeAt`, no guards, no tag/value/text discrimination. Only the closing char is inserted to the right of the caret, which is why the caret lands inside without any mid-insert trick (see [memory: auto-closing pairs](/.claude/memory/project_attr_value_autoquotes_deferred.md)). `'` not paired beyond the four listed; `}` `)` etc. are typed literally. Covered by `EditAtTests` (`Quote_*`, `Brace_*`, `Single_quote_*`, `Backtick_*`, `Pair_fires_anywhere_*`).
- **`\n` → block auto-indent.** Enter mirrors the **previous line's leading whitespace** onto the new line. VS 2026 does **no** indenting itself on Enter (verified live — the request arrives at column 0), so this is the auto-indent. The whitespace is copied **verbatim** (tabs/spaces as the file uses them — no `FormattingOptions` consulted). Pure text op, the parse tree is **not** consulted (`FindNodeAt` unused): plain block indent (same level as the line above), *not* a smart +1 after an open tag. Caret trick: an empty `Replace` at column 0 would leave the caret to the **left** of the indent, so instead the `Replace` **captures the just-typed line break** (`\r\n`/`\n`, re-emitted) up to the caret and appends the indent — range END is the caret ⇒ caret lands **after** the indent. Empty indent ⇒ no edit (column-0 lines stay bare). **Known cosmetic flicker:** VS handles Enter synchronously (caret to col 0), our indent edit applies a round-trip later (caret jumps right); inherent to LSP-side indentation — the synchronous fix (client-side Language Configuration) is unavailable in the OOP model (see [memory: OOP has no Language Configuration](/.claude/memory/project_oop_no_language_configuration.md)). Covered by `EditAtTests` (`Indent_*`).

**Why not route through `ContextAt`.** onTypeFormatting fires *after* the character is in the buffer, with the caret right after it. At that caret the element's span is at its exclusive End (EOF cases `<Button>` / `<Button/`), so `FindNodeAt(caret)` returns `null` and `ContextAt` would say `Outside`. The robust primitive is **`FindNodeAt(column - 1)`** — the position of the typed character, which sits inside the element's span and yields it directly. So `EditAt` reuses `FindNodeAt` (parser owns positions) but does **not** go through the `ContextAt` union. Guards lean on this: a `>` / `/` inside an attribute value or text content resolves to a `XamlValue` / `XamlText`, so those positions never reach an edit; a `/` that resolves to the element but sits *outside* its `OpenTagSpan` (the hand-typed `</`) is rejected by the containment guard above. Covered by `EditAtTests`.

## Type / context provision

The xmlns view of a document is **already in `XamlDocument`** (see above) — pure data, computed by `XmlnsExtraction` during parse. The rest lives in `XamlLanguageServer`: one server-lifetime resolver, a thin CLR-type abstraction layer, and the context provider.

### `AssemblyResolver` — reads assemblies from `@assemblies`
- Plain `IDisposable` class — no longer inherits `MetadataAssemblyResolver`, no `MetadataLoadContext`.
- Public API: `EnsureFolderFor(string vxamlPath)`, `XamlAssembly? GetAssembly(string name)`, `Dispose()` (no-op — there is nothing to release; we hold only the built `XamlAssembly` strings). No raw reflection type leaks out — `GetAssembly` returns the `XamlAssembly` wrapper.
- `GetAssembly` finds `{name}.dll` in a registered folder, reads its bytes, opens a `PEReader` / `MetadataReader`, builds `XamlAssembly`, caches by name in `_loaded`. **No negative caching:** a miss leaves the cache untouched so a later `EnsureFolderFor` discovery can succeed without an invalidation dance.
- See "Assembly discovery" + "Loading & lookup" above for the walk-up and the metadata-reading details.

### Type abstraction layer — `XamlAssembly` / `XamlType` / `XamlProperty` / `FullXamlType` / `MetaSignature`
Plain data extracted from metadata — **no `System.Type` / `PropertyInfo` / metadata handle is retained** past index construction. All `internal` to `XamlLanguageServer`.
- **`XamlAssembly`** — built from a `MetadataReader`. Iterates `reader.TypeDefinitions`, keeps only top-level public, concrete (non-abstract), named (non-empty namespace), non-interface, non-enum types, and builds a `ByNamespace[ns][typeName] → XamlType` index **once eagerly**. API: `XamlType? GetType(ns, typeName)`, `IEnumerable<XamlType> GetTypes(ns)`. Owns all the metadata-reading helpers — `CollectHierarchy` (base-class names + transitive same-file interface closure in one walk), `ResolveContentElementType`, `ReadSettableProperties`, `ReadEnumValues`/`ReadEnumLiterals`, `ReadCustomAttribute`/`HasCustomAttribute`/`AttributeTypeName`, `BuildAttached`/`ReadAttachedPropertyTypes` — and the static `name → role` map. A **`BuildEnumIndex` pre-pass** runs *before* the main loop: a whole-assembly `enum-simple-name → member-names` map, needed because an attached-property value type is referenced **by name** (not by a signature handle) and the enum may be defined after the type that names it. `HasCustomAttribute` is the presence-only sibling of `ReadCustomAttribute` (parameterless markers like `[AttachedTransparent]`).
- **`XamlType`** — document-independent, prefix-free **data holder**: `Name`, role flags, the by-name `_baseNames` set, `ContentProperty`, `ContentPropertyType`, `Properties`, `AttachedProperties`, `IsAttachedTransparent`. Roles are a `[Flags] enum XamlTypeRole` (`RootElement`, `MarkupExtension`, `UiElement`, `Inline`) folded from the base-class names against the role map (by **simple name** — decoupled from namespaces/assemblies; in-dialect collision risk negligible). `IsAChild(name)` = (self-name or anything in `_baseNames` — base classes **and** implemented interfaces, all by simple name) **and** the type is itself usable as a child (not a root element or markup extension — that exclusion is folded in so call sites don't repeat it). `IsVisibleIn(child)` is the content-model authority (see below). `HasTypedContent` = `ContentPropertyType` is a concrete type (not `Object`/null). `AttachedProperties` (`XamlProperty[]`) and `IsAttachedTransparent` (default **false**) drive attached-property completion (see "Attached properties").
- **`XamlProperty`** — settable property surfaced for attribute completion: `Name`, `Type` (the declared type's simple name), `ContentElementType` (the leaf item type when the property is a collection — `Header : TableRowCollection : List<TableRow>` → `TableRow`; **null for scalars**, since only collection properties drive property-element completion), `EnumValues` (member names, non-null only for a same-file enum). `ContentElementType` is decoded by the same `TryResolveCollectionElementType` helper behind `XamlType.ContentPropertyType`. **`Nullable<T>` is unwrapped at read time** (`UnwrapNullable` in `ReadSettableProperties`): a `Boolean?` reads as `Type == "Boolean"` and a `SomeEnum?` keeps the underlying enum's `TypeDefinition` handle so its `EnumValues` are read — vxaml properties are overwhelmingly nullable, so without this value completion would never fire. Only value types are ever `Nullable`, so the collection/delegate decoding is unaffected.
  - **`ReadSettableProperties` collects the full inherited surface**, not just declared members: it walks `BaseType` while it stays a `TypeDefinition` in this file (`Button : CommandControl : ContentControl : Control : UIElement : …`, all same-assembly `TypeDef`s — see [memory: probe, don't theorize](/.claude/memory/feedback_probe_dont_theorize.md)), accumulating settable properties at each level. Dedup is by name with **first-seen-wins**, so a derived declaration shadows the inherited one. The walk ends at the first external base (the terminal `System.Object` `TypeRef`, or a sibling assembly) — those members live in a file we do not open. **Delegate-typed members are excluded** (`Action`, and the generic `Action<…>` whose metadata name is `Action`N`) — they are code callbacks, never XAML attributes; the check runs *before* the dedup add so it never reserves a name from a settable same-named member higher up. Get-only properties are still skipped (a setter is required).
- **`FullXamlType(XamlType Type, string Prefix)`** — a shared `XamlType` paired with the xmlns **prefix** it is bound to *in a specific document*; carries `QualifiedName` (`prefix:Name`, or bare `Name` for the default binding). The prefix attaches **here**, at enumeration time, because it is the one document-scoped fact — the `XamlType` itself is shared server-wide.
- **`MetaSignature`** — `MetaTypeRef` (a name-only decoded type: simple name, namespace, optional `Def`/`Ref` handle, and the arguments of a generic instantiation) plus `MetaSignatureProvider`, the stateless `ISignatureTypeProvider` / `ICustomAttributeTypeProvider` that decodes signature and custom-attribute blobs into `MetaTypeRef`. This is the `SignatureDecoder` plumbing behind `List\`1<TableRow>` → `TableRow` and the `ContentPropertyAttribute(string)` argument read.

**Content model — `XamlType.IsVisibleIn(child)`** decides what may sit inside a container, dispatched from `XamlContextProvider.ContentEntries` after resolving the container element to its `XamlType` via `XamlContextProvider.ResolveType` (the point-lookup inverse of `ReachableTypes`):
- **Typed content model** (`HasTypedContent`) — the content property has a concrete element type, whether a typed collection (`Rows : TableRowCollection : List<TableRow>`) or an interface element type (`Cells : SheetCells : List<ISheetCell>`). Only children that `IsAChild` that element type are valid, and the coarse `IsUiElement` role pre-filter **steps aside** (a typed child like `TableRow`, or an `ISheetCell` implementer, need not be a `UIElement`). (`IsAChild(name)` = `IsA` the name **and** not a root element / markup extension — the latter exclusion folded in so call sites don't repeat it.)
- **Unconstrained model** — `Object` / mixed content (e.g. `List<Object>`, where the element type carries no real constraint). Fall back to the coarse role filter (`IsUiElement`, minus root elements and markup extensions) plus the `Inlines → IsInline` name convention. Richer per-name convention is added only as new narrow containers appear — not generalised ahead of need (see [memory: typical over exhaustive](/.claude/memory/feedback_typical_over_exhaustive.md)).
- **Property element** `<Owner.Property>` — two slots, two **distinct dot signals**, deliberately handled in two places:
  - **Children *inside*** `<Owner.Property>` — handled in `ContentEntries` *before* the container-type branch: the **container name** carries a `.`, so it is split into `Owner` (possibly prefix-qualified, `my:Table.Header`) and `Property`. `Owner` is resolved via `ResolveType`, the `XamlProperty` is found by name, and its `ContentElementType` is the element type children must `IsAChild`. Only **collection** properties qualify (`Header : TableRowCollection` → `TableRow`); a scalar property element (`<Table.GridLines>`) has `ContentElementType == null` and offers nothing — deliberate, only collections are wired (`PropertyElementEntries`).
  - **The property-element tag *name*** — `<Button.|` — handled in `ChildTagEntries` (the `ChildTagNameContext` arm) *before* `ContentEntries`: here the dot is in the **partial tag name** (`ctn.Element`, `Button.`), a different node from the container, so `ContentEntries` never sees it. Owner is the typed prefix before the dot (`Button`, or `my:Button` via `ResolveType`); `PropertyElementNameEntries` offers that type's property **names** as `Owner.Prop` labels (kind `Attribute`, the whole `Owner.` under the caret is the replaced token). **Every** settable property qualifies (scalar or collection) — a property element can host any property, unlike the collection-only children above.

### Attached properties — `Grid.Row="1"` on a child

A2v10 attached properties are imperative get/set, so **metadata carries no value type** — parsing the real logic is hopeless. Two facts come from authored attributes instead, read by simple name (no `System.Type`, activates the day the attribute appears on a real type):

- **Names — `[AttachedProperties("Col,Row,ColSpan,RowSpan,VAlign")]`** (runtime-owned, already consumed by A2v10 — we must **not** overload it). The authoritative list of attached names a container declares for its children.
- **Value types — `[AttachedPropertyType("VAlign", "VerticalAlign")]`** (advisory, **read only by us**, `AllowMultiple`). A **sparse overlay**: only the ~10% of attached that have completable values (enums, `Boolean`) are annotated; the rest default to type `"Object"` (name completion only). The second arg is a **plain string, not `typeof`** — we resolve enums by simple name *everywhere*, so a namespace would be thrown away and `typeof` would only buy `GetTypeFromSerializedName` plumbing for nothing. Enum *members* still come from the enum's real metadata via `BuildEnumIndex`. `XamlAssembly.BuildAttached` merges the two into a `XamlProperty[]` per type, so the value slot reuses `ValueEntries` unchanged.

`XamlType.IsAttachedTransparent` (from a parameterless `[AttachedTransparent]` marker) controls **propagation depth** to descendants. **Default false is the only meaningful polarity**: with default true the marker would be a permanent no-op (everything already transparent). So by default attached reach **direct children only** (the WPF rule); the marker opens deeper propagation on the few containers that forward an outer container's attached. The completion walk (`XamlContextProvider.AttachedEntries`) climbs the `Parent` chain, the direct container always contributing, continuing up only **through** an `IsAttachedTransparent` ancestor — a general loop whose effective depth is data-driven and **tightens automatically** as A2v10 marks transparent wrappers. Diagnostics (when built) are unaffected by transparency: runtime silently ignores a misplaced attached, so there is **no placement diagnostic** — only owner-from-name existence.

**Two positive paths are wired but not yet unit-tested** — the fixture `A2v10.Xaml.dll` carries neither new attribute, so attached **value** completion (no `[AttachedPropertyType]` overlay → all `"Object"`) and the transparent **climb** (no `[AttachedTransparent]`) are unexercised; the default/negative branches are covered. They light up when A2v10 ships the attributes, or against a purpose-built tiny fixture.

### `XamlContextProvider` — completion entries for a position
- Constructor takes `AssemblyResolver`. Server-lifetime singleton.
- Public API:
  - `IEnumerable<FullXamlType> ReachableTypes(XamlDocument doc)` — every type reachable through the document's `ClrPrefixes`, each paired with its binding prefix. **No role filtering** — entry builders apply their own. Aggregates across **all** prefixes. Building block; consumed by the entry builders and by tests.
  - `XamlCompletionResult Complete(XamlDocument doc, int line, int column)` — the single position-aware entry point. Calls `doc.ContextAt(line, column)` and dispatches via a `switch` over the `XamlPositionContext` variant. Returns `XamlCompletionResult(Entries, EditSpan)`.
- `XamlCompletionEntry(Label, XamlCompletionKind, Detail?)` + `XamlCompletionKind { Tag, Attribute, EnumValue }` — domain-neutral; `CompletionHandler.MapKind` turns each into a `CompletionItemKind`.
- `XamlCompletionResult(IReadOnlyList<XamlCompletionEntry> Entries, TextSpan EditSpan, Char? ValueQuote)` — the entries plus the **single source range they all replace**, which is `doc.IdentifierSpanAt(line, column)` (the token under the caret). **One range per response, not per entry** — the replaced token is a property of the *position*, not the item. The handler stamps `EditSpan` onto every item's plain `TextEdit` (`InsertReplaceSupport` is false) so the **editor never computes the range from its own word heuristic** — which ate the quotes in `Disabled="|"`, would split prefixes on `:` (`my:Button`), and duplicated the token in `{Bind Dat|}`. Deriving the range from a pure text scan instead of the parse tree makes completion insertion **deterministic and unit-testable** (no live-VS round-trip) and editor-independent. (`CompletionList.ItemDefaults.editRange` is a possible later optimisation; the source range is the same.) `ValueQuote` is the quote char of an attribute-value slot (`"`/`'`, else null) — a pure **structural** fact; the **handler** decides whether to append a matching closing quote, keyed on the trigger char (the quote-race fix — see "Open issues").

**`Complete` dispatches on `ContextAt`** — the parser owns all position semantics (see "Position classification"); the provider only decides *what to offer*. Implemented arms:
- **`TagNameContext` → root tags / `ChildTagNameContext` + `ElementContentContext` → child tags.** Root vs. child is decided by the **variant**, not a nullable field (see "Position classification" for the 2×2 and why the old single-variant-with-nullable-container shape was split): `TagNameContext` → `RootEntries(doc)` (filters `IsRootElement`); `ChildTagNameContext` or `ElementContentContext` → `ContentEntries(doc, ...)` for the container's content. When the container is a **property element** (`<Table.Header>`), `ContentEntries` routes to `PropertyElementEntries` (see "Content model" above). Labels are prefix-qualified via `FullXamlType.QualifiedName`. Enumerate the full candidate set, never point-look-up the in-progress name — the editor filters (see [memory: no partial-name lookup](/.claude/memory/project_completion_no_partial_lookup.md)).
- **`AttributeNameContext` → settable properties** of the element **plus attached properties from ancestor containers** (`PropertyEntries(ResolveType(doc, anc.Element))` ++ `AttachedEntries(doc, anc.Element)`). `AttachedEntries` walks the `Parent` chain (see "Attached properties"), labelling each attached owner-qualified (`Grid.Row`, `my:Grid.Row`), deduped by label. The dot is already a name char in `IsNameChar`, so `<Block Grid.Ro|` reaches `AttributeNameContext` and the edit range covers `Grid.Row` whole — **no parser change**. **`TagInteriorContext` returns empty** — deliberately: the empty interior slot is reached mostly by Backspace/Del re-trigger, where an auto-popped list is noise; the attribute-name probe (see "Position classification") routes *typing* to `AttributeNameContext`, so the list still appears while typing.
- **`ExtensionTypeNameContext` → markup-extension types** (`ExtensionTypeEntries`, filters `IsMarkupExtension`).
- **`ExtensionInteriorContext` / `ExtensionArgNameContext` / `ExtensionPositionalArgContext` → the extension type's properties** (all three via `ExtensionPropertyEntries(doc, ext)`, resolving the owner through the extension's `TypeNameSpan`). All three are "argument name" slots: in the realistic editor flow (quote/brace auto-closed) a freshly typed name keeps the caret at the token end → `Interior`; editing an existing `Name=` → `ArgName`; a bare token → `PositionalArg`.
- **`AttributeValueContext` / `ExtensionArgValueContext` → the property's values** (`ValueEntries(XamlProperty?)`). The property is resolved per slot by a small helper, then `ValueEntries` is a pure value→entry builder: enum members, or `True`/`False` for `Boolean`, otherwise nothing (string / type-converter values not yet wired). The resolvers — `PropertyByName(owner, name)` for a plain attribute / extension arg; **`AttributeValueProperty(doc, element, attrName)`** which, for a **dotted** attribute name (`Grid.VAlign`), splits owner-from-prefix and looks the property up in the owner's `AttachedProperties` (the same owner-from-name split as property elements), else the element's own `Properties`. Entries are `XamlCompletionKind.EnumValue` with **no `Detail`** (no placeholder cliché). Nullable enums/bools work because `Nullable<T>` is unwrapped in `XamlProperty` (see above).

The no-op arms (`Outside` / `Text` / `Comment` / `CData` / `EndTagName`, and `TagInterior`) return empty. The scaffold convention: each arm hands its method the concentrated data it processes (element / attribute / extension), not the bare base context. `PropertyEntries(FullXamlType?)` is the shared property→entry builder; `ExtensionPropertyEntries` is the thin owner-from-extension wrapper over it; `AttachedEntries` is the ancestor-walk attached-property builder; `ValueEntries(XamlProperty?)` is the shared enum/bool value builder (the property is resolved by the per-slot helpers above).

The path of the vxaml file is needed exactly once — on `didOpen`/`didChange`, to call `_resolver.EnsureFolderFor(...)`. After that provider methods take only the parsed `XamlDocument`.

**Commit characters (`CompletionHandler` registration).** VS 2026 ignores per-item commit chars (`CommitCharactersSupport=false`) but honours a **shared** set via `CompletionRegistrationOptions.AllCommitCharacters` — set to `["=", "/", ">", " "]`. With an item selected, typing one commits the label (`<Button Dis|` + `=` → `Disabled=`), matching classic VS. It is global across all completion lists; only `=` was specifically wanted (attribute names), the rest are harmless in the other contexts. Note this is **independent** of the auto-closing-pair onTypeFormatting: `=` commits the attribute *name*, then the user types `"` and the closing quote auto-appears — two separate standard-LSP steps (see [memory: auto-closing pairs](/.claude/memory/project_attr_value_autoquotes_deferred.md)).

### What is **NOT** in the design (and why)

- **No `ITypeProvider` interface.** Was a YAGNI artefact justified by "two implementations (real + test fake)" — but the singleton lives in the server project, server tests can use a real fixture DLL, no fake provider needed for parser-side tests.
- **No `SemanticModel` / `SemanticModelFactory`.** Their role split between `XamlDocument` (xmlns fields, `FindNodeAt`) and `XamlContextProvider` (types). Adding a third layer was duplication.
- **No `XmlnsScope` / `XmlnsBinding` hierarchy / `XmlnsResolver` separate class.** Three flat fields on `XamlDocument` do the job; the abstract base + two sealed subclasses + scope container were over-engineered.
- **No per-document type provider, no per-document reader.** One server-lifetime `AssemblyResolver` with a by-name `XamlAssembly` cache. Type coordinates are absolute, so one cache serves all documents.
- **No `FileSystemWatcher` on the @assemblies folder.** The by-name cache never reloads a changed DLL, and vxaml types come from a stable controlled package — a server restart is the refresh path. (Note: we no longer lock the DLL — bytes are copied once — so a watcher would now be *possible*, but it is still not wanted: it would only invalidate the cache, which restart already does.)

### What still needs to be built

`Complete` is now on `ContextAt`; the tag arms (`TagNameContext` → root, `ChildTagNameContext` / `ElementContentContext` → child) are implemented, and child tags are content-model filtered via `XamlType.IsVisibleIn` (typed collections / interface element types fully; unconstrained content via the coarse role filter — see "Content model" above). **Property elements** (`<Owner.Property>`) are wired **both ways** — completing the property-element **tag name** (`<Button.|` → the owner's property names, `PropertyElementNameEntries`) and the **children inside** a collection property element (`PropertyElementEntries`). **Attached properties** are wired end-to-end — name completion on children, value completion on dotted names, transparency-gated depth (see "Attached properties"). Remaining:

- **Inherited content-property / get-only properties** — `ReadSettableProperties` now walks the base-class chain (inherited settable properties *are* surfaced — see the `XamlProperty` note above), but `[ContentProperty]` and the content-element-type read still consult the type itself only (`ReadCustomAttribute(td)`), so a content property *declared on a base class* won't be picked up; get-only properties are still skipped. Acceptable for the current dialect (content collections are declared with setters on the leaf type); revisit if a real case appears.
- **Deeper unconstrained-content convention.** Only the `Inlines → IsInline` name rule exists for `Object`/mixed containers; add more `content-property-name → allowed role` rules as narrow containers appear, but don't generalise ahead of need.
- **Markup-extension completion** — extension *type names* are wired (`ExtensionTypeEntries`, `IsMarkupExtension` filter); open design questions remain on the optional `Extension` suffix and `x:`-namespace forms.
- **Value completion beyond enum/bool** — known type-converter values (brushes, etc.). Enum members and `True`/`False` are wired (`ValueEntries`); string / converter values are not.
- **Semantic diagnostics — `Class not found` / `Property not found`** (the original motivation for the attached-property work). Decided shape: **Error severity** — vxaml is not compiled, so an unresolved type/property is a guaranteed **runtime** crash and the language service is the *only* checkpoint before it; the register matches the consequence. Gate hard so a red squiggle never lands on valid code: only when a type universe exists (`@assemblies` found) and the prefix's assembly actually loaded — every "don't know" case stays silent (a missing-but-real type elsewhere is a cheap, self-correcting false red; suppressing real typos is the costly direction). **Class-not-found** is ready to build (high confidence). **Property-not-found** is now unblocked by attached properties: a dotted attribute routes to owner-from-prefix + `AttachedProperties` membership, so it won't false-positive on `Grid.Row`. Producer is a new tree walk in the server (needs the type layer), merged into `TextDocumentSyncHandler.PublishDiagnostics` alongside the parser's structural diagnostics.
- **Attached properties — A2v10-side + positive tests.** For the wiring to light up, A2v10 must ship the `AttachedPropertyTypeAttribute(string name, string type)` (`AllowMultiple`, runtime-ignored) on the ~10% of attached with enum/bool values, and `[AttachedTransparent]` on transparent wrappers. Until then the positive value/transparency paths are untested (see "Attached properties").

Done this round (formerly listed here): **property-element tag-name completion** — `<Button.|` now offers the owner type's settable property names (`PropertyElementNameEntries`), reached from the `ChildTagNameContext` arm via `ChildTagEntries`, which splits on the dot in the **partial tag name** (`ctn.Element`, `Button.`) — a different signal from the container-name dot that `ContentEntries` reads (children *inside* a property element). Owner is the typed prefix before the dot (`my:Button` handled by `ResolveType`); labels are `Owner.Prop`, kind `Attribute`. **Every** settable property qualifies here (scalar or collection), unlike the children *inside* a property element (collection element type only). Earlier rounds: all value arms (`AttributeValueContext` / `ExtensionArgValueContext`) wired via `ValueEntries` with `Nullable<T>` unwrapping; **completion `TextEdit` / replacement ranges** — every item now carries an explicit range from `IdentifierSpanAt`, so the `:`-word-boundary problem for prefixed names (`my:Button`) and the quote-eating in value slots are both solved; **attached properties** — reading (`[AttachedProperties]` names + sparse `[AttachedPropertyType]` value-type overlay + `BuildEnumIndex`), name completion on children via the `IsAttachedTransparent`-gated ancestor walk, and dotted value completion (see "Attached properties").

### Attribute-driven enrichment — `[Description]` (planned), `[Browsable(false)]` (done)

These attributes are authored on the dialect classes/properties in `A2v10.Xaml.dll` and read through the **existing custom-attribute path** (`ReadCustomAttribute` / `AttributeTypeName`) — no new infrastructure, the metadata reader already decodes string/bool ctor args. They are a **consumer-facing** channel, deliberately separate from XML-doc (`///`): XML-doc is written for the library *developer* (inheritance, C# semantics), whereas the audience here is the *vxaml author* — so the text is net-new authoring, not reused dev docs. See [memory: descriptions are consumer-facing](/.claude/memory/project_descriptions_consumer_facing.md). Both attributes live in the controlled package, consistent with the "stable controlled package" assumption — and both degrade silently when absent, so adoption can be incremental.

**`[Description("…")]` → hover + completion detail.**
- Read at type level via `ReadCustomAttribute(reader, td, "Description")` (already shaped for the string ctor arg); at property level via `pd.GetCustomAttributes()` inside `ReadSettableProperties`.
- New `Description` (`String?`) on `XamlType` and `XamlProperty`.
- Consumers: replaces the placeholder `Detail` on `XamlCompletionEntry` (the `"Xaml element"` / `"Xaml Property"` clichés — drop them, see [memory: copy style](/.claude/memory/feedback_copy_style.md)), and feeds the planned `HoverService` (plaintext-only under VS 2026 — see client capabilities). A null `Description` ⇒ no detail / no hover, degrades silently.

**`[Browsable(false)]` → drop from the index (done).** A non-browsable type/property is **never indexed**, not flagged-then-filtered. `ReadBoolAttribute` (the bool-arg sibling of `ReadCustomAttribute`) reads the ctor arg by name; `IsCandidate` rejects a `[Browsable(false)]` **type** so it never enters `_byNamespace`, and `ReadSettableProperties` `continue`s past a `[Browsable(false)]` **property**. No `IsBrowsable` flag on `XamlType`/`XamlProperty`, no `.Where` in any entry builder.
- **Why drop at the source, not filter at the builders.** Carrying a hide-flag through the data model and re-filtering at every entry builder (`RootEntries` / `ContentEntries` / `ExtensionTypeEntries` / `PropertyEntries` / `PropertyElementEntries`) is addition; dropping at the one choke point is removal — the first instinct here was the flag, and that was the wrong instinct (see [memory: drop at the source, don't carry a hide-flag](/.claude/memory/feedback_drop_at_source_not_flag.md)).
- **Consequence (accepted):** a dropped type is invisible to **resolution** too — `ResolveType` won't find it, so it can't be a content-model element type or owner. Fine in practice: `[Browsable(false)]` marks types the author wants hidden from authoring entirely, which are not containers the user types into. It is a *hint to hide*, not a validity rule (a member typed explicitly is still legal), so it never drives a diagnostic.

**Door this opens (not in this step).** The same attribute-reading path generalises to validation: `[Obsolete("…")]` → a warning diagnostic on use; `[Required]` / range attributes → attribute-value checks. Add these only when the attributes actually appear in the library — don't build ahead of the metadata (see [memory: typical over exhaustive](/.claude/memory/feedback_typical_over_exhaustive.md)).

## Multi-client hosting — `IClientProfile` (idea, not yet implemented)

A second host is planned: a **standalone stdio Language Server for VSCode** alongside the VS 2026 VSIX. The transport boundary is already clean for this — `XamlLanguageServer` and `XamlTolerantParser` reference **nothing** VS-specific (no `Microsoft.VisualStudio.*`, no `Nerdbank.Streams`); the only VS mention in the server is a *word inside a doc comment*. `XamlLangServer.Start(Stream, Stream)` takes abstract streams, so a VSCode host just calls it with `Console.OpenStandardInput()/Output()` instead of a `FullDuplexStream` pair. All VS-transport code is confined to `XamlServiceExtension.XamlLanguageServerProvider.CreateServerConnectionAsync`. So the port adds a new thin host, and **does not touch** the two language projects.

What *does* differ between clients is not transport but **handler calibration** — and the decided approach is to **not branch on raw `ClientCapabilities`** (too general; combinatorial 2ⁿ flag space ⇒ testing hell). Instead, introduce an **`IClientProfile`** abstraction with a small implementation per client (`VsProfile`, `VsCodeProfile`). The profile collapses the capability matrix into **2 named, intention-revealing decisions sets** that are tested as wholes: a handler depends on a *named decision* (`profile.AppendClosingQuoteOnValueTrigger`), never on the shape of the capability graph, so handler tests inject a tiny profile and profile correctness is a one-time data assertion. Linear, not combinatorial.

- **Name:** `IClientProfile` (decided). Avoid `…Options` — collides with OmniSharp's own `LanguageServerOptions` (the `opts` in `LanguageServer.From`) and reads like config knobs rather than a behavioural profile of the target client.
- **Selection is by HOST, not by an `initialize` probe.** The host is the only layer that legitimately knows its client: the VS extension injects `VsProfile`; the VSCode console-exe injects `VsCodeProfile` (hardcoded or `--client=vscode`). One `VsCodeProfile` covers the whole VSCode family (Cursor/VSCodium). Capabilities may still be dumped once as a log-time sanity probe (as the VS profile was originally snapped — see the comment block above `XamlLangServer`), but they stop being the dispatch mechanism. Wiring: one extra param `XamlLangServer.Start(stream, stream, IClientProfile)`, registered as a singleton in `WithServices`, read by handlers via DI and by `OnInitialize` (which then stops hardcoding the semantic-tokens flag clear).
- **Interface vs record:** most decisions are pure data (bool/enum), so a `sealed record` with `static readonly Vs`/`VsCode` would suffice — but `HoverFormat` already foreshadows *behaviour* (`string FormatHover(...)` differs per client), and there are genuinely two implementations, so an interface is justified under the project's own DI convention.
- **Discipline (matches [memory: typical over exhaustive](/.claude/memory/feedback_typical_over_exhaustive.md)):** a flag enters `IClientProfile` **only when a handler actually branches on it** — otherwise the profile distends into a full mirror of `ClientCapabilities` and the testing hell returns under a new name.

The decisions that diverge today (all three are VSCode-port blockers — calibration, *not* transport):

| Decision | VS 2026 | VSCode |
|---|---|---|
| `AppendClosingQuoteOnValueTrigger` (the quote-race closing-quote append, keyed on the `"`-trigger — see Open issues) | `true` | `false` *(verify live — VSCode has its own applicable-span + client-side auto-close)* |
| `ServerSideAutoClosingPairs` (`"` `'` `` ` `` `{` via onTypeFormatting) | `true` | `false` — VSCode does this client-side via `language-configuration.json` (a server+client double-insert otherwise) |
| `ForceStaticSemanticTokens` (clear `SemanticTokens.DynamicRegistration` in `OnInitialize`) | `true` | `false` — VSCode honours dynamic registration (forcing static is harmless but should be a profile decision, not a hardcode) |

Future profile members (add when the feature lands, not before): `HoverFormat { Plaintext, Markdown }` for the planned `HoverService`; snippet (`$0` tab stops) and per-item commit-character richness (VSCode supports both, VS 2026 does not).

**Other VSCode-port notes (not `IClientProfile`, but client-side):** auto-closing pairs, brackets and comment markers move into a `language-configuration.json` shipped by the VSCode extension; a TextMate grammar becomes *available again* there (it was abandoned only because VS Extensibility couldn't deliver it — see "Rejected approaches") as an optional instant-colour layer under semantic tokens, though semantic-tokens-only also works. .NET runtime distribution (framework-dependent vs self-contained per-platform vsix) is a packaging decision for the VSCode host, independent of the server.

### Local dev loop under VSCode (no marketplace, no `vsce`)

To run the server under VSCode *on a dev machine* — and specifically to **probe the real VSCode `ClientCapabilities`** before any calibration — needs only F5, not publishing. Prereqs: .NET SDK, VSCode, **Node.js + npm** (the client extension pulls `vscode-languageclient` via `npm install`). Two small new artifacts on top of the existing server:

1. **stdio host** — a tiny console project referencing `XamlLanguageServer`, body essentially `await new XamlLangServer().Start(Console.OpenStandardInput(), Console.OpenStandardOutput())`. Three differences from the VS host: (i) **`await` to exit** — not fire-and-forget; in a separate process there is no deadlock reason and the process must outlive the server; (ii) **never write to `stdout`** except LSP — any `Console.WriteLine` poisons the protocol, logs go to `stderr`/file; (iii) in dev it is launched as `dotnet …\bin\Debug\net8.0\<host>.dll`, straight from `bin`, no publish.
2. **Minimal VSCode extension** — a folder with `package.json` (`engines.vscode`, `main`, `contributes.languages` = id `vxaml`/`.vxaml`, `activationEvents: ["onLanguage:vxaml"]`, dependency `vscode-languageclient`), `extension.js` (a `LanguageClient` whose `ServerOptions` spawn `dotnet <host>.dll` over stdio, `documentSelector` = `vxaml`), and `.vscode/launch.json` (Run Extension). Then `npm install`.

Run: open the extension folder, **F5** → second window (**Extension Development Host**) → open a `.vxaml` → extension activates → client spawns the `dotnet` server → `initialize` fires. **First action once this works: dump `request.Capabilities` in `OnInitialize`** (same throwaway probe that produced the VS 2026 block above `XamlLangServer`) → that yields the **real** VSCode profile. Until that dump exists, the VSCode capability values are **unknown and must not be assumed** — "VSCode is the reference LSP client / those flags are true" is a guess, not data (the project's quote-race saga already shows a "proven" client-behaviour theory being wrong — see [memory: probe, don't theorize](/.claude/memory/feedback_probe_dont_theorize.md), [memory: root cause before patching](/.claude/memory/feedback_root_cause_before_patching.md)). The `IClientProfile` calibration is gated on this probe.

## DI & services

- Extension-level services (logging etc.) are registered in `ExtensionEntrypoint.InitializeServices(IServiceCollection)`.
- Register as concrete class (no interface) when there is only one implementation and no mocking need. Extract interface only when multiple implementations or unit test mocks are required.
- Architecture principle: **design correctly from the start**. Do not defer proper abstractions with "we'll refactor later."

## Open issues

- **`XamlLanguageServerTests`.** `XamlContextProviderTests` (real fixture: reads `XamlTolerantParserTests/@assemblies/A2v10.Xaml.dll` through the production `AssemblyResolver` / `MetadataReader`, no fakes) covers `ReachableTypes`, the tag-name / child-tag `Complete` cases, the content model (`Table → TableRow` typed collection; `SheetRow → ISheetCell` interface element type, incl. a child inheriting the interface through a base class), the **property-element tag name** (`<Table.|` → `Table.GridLines` / `Table.Header`, not bare `GridLines`, `EditSpan` = `Table.`), inherited-property collection (`Button` offers `Command`/`Content`/`Width` from up the chain), extension-property completion, the **value slots** (`GridLines=""` → enum members, `Title=""` String → empty), and the **edit range** (`EditSpan` covers the value content between quotes / the partial tag name / the extension arg token — the regression guards for the quote-eating and `{Bind Dat|}` duplication). `SemanticTokensTests` covers the colouring mapping structurally (palette-agnostic — see Architecture). Still thin on hover / diagnostics (not built).
- Debounce / cancellation for push diagnostics.
- Potential version conflict between transitive dependencies of OmniSharp ↔ VS Extensibility SDK. Has not triggered yet — keep in mind.
- **Auto-popping the value list right after the auto-inserted closing quote (`Wrap="|"`) — DONE.** Typing `"` after `Wrap=` pops the enum-value list immediately (no Ctrl+Space), and committing keeps the closing quote. `"` lives legitimately in `CompletionHandler.TriggerCharacters` (alongside `<`).
  - **The earlier "proven root cause" was wrong — and was wrong because it reasoned about the PARSE TREE, not the real buffer** (see [memory: probe, don't theorize]). The old note claimed both Ctrl+Space and `"`-trigger see an *identical* buffer (`Wrap=""`, pair already inserted) so the quote-eating is "entirely client-side", citing a two-buffer test that fed `Complete` two *hypothetical* buffer strings and watched `ContextAt`. That test never observed what VS actually sent.
  - **Real root cause (observed, by logging `doc.Source` + `request.Position` at the live completion request — temporary `Dump` probe to `%TEMP%`, since removed).** The `"` keystroke fires **two independent server reactions that RACE**: (1) the completion trigger (opens the popup; VS snapshots its own applicable span at that instant), and (2) onTypeFormatting's auto-pair (inserts the closing quote a round-trip later). The trigger-completion request therefore frequently arrives against the **one-quote** buffer `Background="` (`len 79`, `XamlValue.IsUnterminated == true`) — the closing quote is **not yet there**. (Logs showed the same caret position served against both `Background="` len 79 and `Background=""` len 80.) This disproves *both* old "proven" claims — "identical buffer" and "no race; pair-insert always precedes completion". The server response is byte-identical either way (`ContextSupport=false`, so it can't tell what triggered the session); the difference is purely the racing buffer state, and on commit VS overwrites its applicable span — which now overlaps the just-inserted closing quote — and eats it.
  - **First fix (shipped, then found buggy) — keyed off `IsUnterminated`.** `Complete` set a `InsertSuffix = value.Quote` for `AttributeValueContext { Value.IsUnterminated: true }`; `CompletionHandler` appended it. It worked for an attribute that is **last in the tag** but **silently failed for any attribute in the middle** (`<Button Background="| Width="100" />`): the closing quote disappeared. Root cause of the failure — **`IsUnterminated` is an unreliable race signal.** Scanning the value, the lexer's string terminator is `quote || '<'` (newline does **not** terminate — see `XamlLexer.IsStringTerminator`), so a half-typed mid-tag value pairs the just-typed opening quote with the **next attribute's** opening quote (`Background=" Width="`) and reads `IsUnterminated == false` — even though *this* value has no closing quote. The suffix then never fired where it was most needed. Every parse-derived signal (`IsUnterminated`, empty `ContentSpan`) is poisoned by the same mispairing.
  - **Fix (shipped, current) — keyed off the trigger character, in the handler.** The closing-quote append is a **client quirk**, not semantics, so it lives in `CompletionHandler`, not the provider. `Complete` now exposes only the structural fact `XamlCompletionResult.ValueQuote = value.Quote` (the slot's quote char, else null). The handler appends a matching quote **iff `request.Context.TriggerCharacter == ValueQuote`** — i.e. only when the session was opened by *typing* the quote (the racing `"`-trigger session). This is the one reliable signal, and it lives **outside** the poisoned parse. Verified live in VS for all three cases: last attribute, mid-tag attribute (the regression), and Ctrl+Space. (This naturally seats in the future `IClientProfile.AppendClosingQuoteOnValueTrigger`.)
  - **Why Ctrl+Space is already correct and must NOT get the suffix (observed live).** A Ctrl+Space session opens against the **settled** `=""` buffer (auto-pair long since landed); VS snapshots its applicable span on the empty token *between* the quotes, never touching the closing quote → commit keeps it. There is **no trigger char**, so the handler appends nothing — no doubling. The eat is specific to the `"`-trigger session, whose applicable span is snapshotted mid-race and ends up overlapping the closing quote.
  - **Rejected en route:** `CompletionList.ItemDefaults.editRange` (OmniSharp 0.19.9 *does* expose it — `CompletionListItemDefaults.EditRange`) — tried live, did **not** override VS's applicable-span heuristic, so it doesn't address the race. The empty-span per-item `TextEdit.Range` alone does **not** stop the eat either — a probe disabling the suffix showed the quote vanish in **every** position, confirming the append is load-bearing, not an artefact. `_vs_onAutoInsert` is VS-proprietary (we want VSCode too). LSP gives the server no way to open the popup itself, so the trigger char remains the only mechanism (removing `"` from `TriggerCharacters` would kill the wanted auto-pop).
  - **Residual risk (not yet hit):** the nastiest corner of the race — a `"`-trigger request where by commit the closing quote *is* inserted *and* VS does *not* eat it — would double the quote. Not observed in practice; revisit only if it surfaces.
